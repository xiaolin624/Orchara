# 开发顺序与完成门禁

执行顺序以 [contracts/task-graph.json](contracts/task-graph.json) 为权威。每项列出依赖、交付路径和验收；必须先看产品仓库PROGRESS和实际代码，不因规格中初始状态为空而重建已完成模块。

## 1. 顺序原则

`D00 → P01 → F00/F01 → 版本草稿、运行与编译模块 → 脚本/模型 → TaskRunner → 发布门禁 → 路由/子应用/RAG/记忆 → 十节点整合 → 完整API与治理 → 全量验收/训练/交付`。

P02–P05可在最小fixture上验证框架/存储/隔离，不依赖完整产品。通过P0不等于用户权限或恢复已在平台集成通过。之后按F任务重复的是新集成边界，不是无理由重复跑同一测试。

## 2. 避免循环依赖

- F02拆成A：不可变草稿/快照/注册；B：依赖真实TaskRunner报告的发布门禁。先有私有debug snapshot才能评测，不能要求先发布才能测。
- F04拆成A：线性四节点/适配接口；B：其余节点接线与完整分支语义。子应用、知识节点不反过来成为最小编译器前置条件。
- F13拆成A：最小TaskRunner/checker；B：完整故障/安全/容量。发布门禁依赖A，不等待所有功能测试完成。
- F15拆成A：开发部署冒烟；B：完整升级/备份恢复交付。首周不会等全部功能完成才第一次部署。

任务图不使用“F13持续开展”掩盖真实依赖。所有任务完成后才称完整首版交付；第一周M1仅为纵向切片，额外能力不能以时间到期删除。

## 3. 首周M1完成条件

独立机器配置可复现；两用户隔离；画布可保存并固定版本；自然语言/明确选择应用完成请求；CSV和XLSX统计金额正确、报告可下载；坏输入、超时、取消与失联挂起可解释；发布有真实测试报告；所有未完成能力列明。

M1使用预置工具与受控模型stub也可以先形成开发验收，但报告必须标stub，并另留真实模型/隔离门禁。若无Linux验收，不开放任意脚本上传，不将该profile称正式生产交付。

## 4. 每项DoD

代码/迁移与契约一致；对应接口/错误/权限有必要测试；外部依赖能以stub或真实profile分别检验；报告记命令/版本/输入/观察；PROGRESS记录完成或阻塞；不遗留只有聊天里知道的启动步骤。不能以页面存在、测试数量或README完成代替任务DoD。

单元通过不自动满足集成门禁。缺条件标blocked并继续无依赖任务；若框架/设计不成立，记录反证并缩小可用能力或提出必要改动，不能默默绕过。
