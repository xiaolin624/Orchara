# C1：规格同步 module 设计与实现

日期：2026-11-08；任务：[GitHub #137](https://github.com/xiaolin624/Orchara/issues/137)。

需求依据：[架构审阅与决策记录](2026-11-08-architecture-grilling.md) 的 Q1–Q6、R1–R6。本文记录实施方案；运行结果另见验收报告，不以设计文字代替通过证据。

## 三种 interface 的比较

### 方案 A：保留两个入口，深化内部 implementation

```python
findings = check(source, dest)
result = sync(source, dest)
```

保留现有命令、参数和返回形状。调用者只表达检查或同步，不编排来源扫描、两份复制件、基线、暂存、切换和恢复。错误结果、调用顺序约束与性能也属于 interface：检查不修复；同步失败抛出 `SyncError`；检查返回非空 findings；操作竞争时快速失败。

**depth：** 一个调用完成完整来源核验或受保护的同步，调用者无需学习事务对象。**locality：** 三份内容关系与切换约束集中在原 module。**seam：** 检查和同步两个操作。

### 方案 B：公开观察、比较、计划、执行

```python
snapshot = module.capture(layout)
report = module.compare(snapshot)
plan = module.plan(snapshot, action)
result = module.execute(plan)
```

支持查看计划和显式恢复，但多出快照、计划过期与执行顺序的 interface 知识。目前没有真实计划消费者，公开这些步骤的 leverage 不足；容易把内部结构变成调用者必须遵守的协议。所需清单与核验思想可以保留在 implementation 内。

### 方案 C：工作区对象与统一结果

```python
workspace = SpecWorkspace(source, dest)
result = workspace.check()
result = workspace.sync()
```

布局固定在对象内，结果可统一表达 generation 和恢复信息。常用调用清晰，但现有命令不需要对象生命周期；为兼容还需保留函数转发。相对 A 增加命名和迁移成本，没有新增行为 leverage。

### 选择

采用 **A**。吸收 B 的同一份规范化内容清单、C 的明确恢复与失败结果，但均隐藏在 implementation 内。三个独立设计代理完成比较后，由主代理选择并实施；用户不需要再决定可逆的内部函数拆分。

Deletion test：移除来源核验、比较或恢复职责，会把复杂度推回调用者；这些职责应当保留并深化。只转发参数的 workspace 对象或公开 plan 步骤，在现有调用场景下不能增加 depth。

## Interface 的行为

保留 `check(source, dest, *, spec_subdir, contracts_subdir)` 和 `sync(...)` 的既有参数及默认位置。命令仍为 `python tools/sync_spec.py` 和 `python tools/sync_spec.py --check`。

- `check() == []` 同时表示当前来源、规格复制件、运行契约复制件和基线一致，且没有待恢复事务。
- 检查不会修复受管目录。它可建立私有互斥锁状态，供多个工具进程协作；不改动复制件。
- 无法核实来源、非法路径、损坏基线、进程占用和未完成事务均返回 findings，命令退出非零。
- `sync()` 返回原有计数和 manifest 路径，新增 `recovered` 和 `warnings` 说明恢复及提交后清理结果。失败统一抛出 `SyncError`，命令格式化并返回非零。
- 再次显式同步会尝试恢复上一次中断，然后同步有效来源；检查本身不恢复。来源无效时不开始恢复目标。
- 不新增离线模式、公开文件系统 port、计划对象或恢复命令。

## Implementation 隐藏的规则

### 一份规范化清单

相对路径与规范化 SHA-256 共同定义内容身份。来源只完整扫描一份清单，运行契约从其中 `contracts/` 投影；基线内两份清单也必须符合这一关系。

沿用 UTF-8 文本换行归一化与不可解码字节的原样摘要规则。时间、绝对来源路径、仓库提交号只用于说明。目录遍历在进入缓存、产品目录等排除树之前剪枝，遍历失败不能被当作空目录。

只有规格复制件自身的顶级 `SYNC-MANIFEST.json` 不参与它自己的内容摘要；运行契约中的同名文件仍逐文件核对。

### 路径与写入范围

两个受管位置必须是产品目录内的非空相对路径，不能互相包含，也不能与私有状态目录重叠。来源不能位于目标内；目标也不能位于来源的关键 `contracts/` 内，避免通过剪枝丢掉必需来源。

默认的“仓库根来源包含 product 目标”仍可用；自定义嵌套目标在来源遍历时明确剪枝。纳入来源和目标路径拒绝 symbolic link、Windows junction / reparse 重定向；排除树不跟随、不遍历。

每次递归清理或目录移动之前重新核实固定受管槽位、实际绝对路径与包含关系。恢复记录不提供任意绝对删除路径。此约束防止误配置和普通协作错误，不宣称为抵抗同机恶意进程的文件系统隔离设施。

### 同步与恢复

私有状态位于 `product/.scratch/spec-sync/`，在两份受管复制件之外。它包含稳定的操作系统锁文件、待完成记录以及固定的 stage、old、discard 目录。

1. 在触碰目标前验证完整来源及根 `contracts/`。
2. 取得产品目录的非阻塞进程锁；检查和同步使用相同的互斥规则。
3. 如存在上次未完成记录，核实其布局、内容身份与备份，先恢复上次切换前的状态。
4. 在私有位置准备两份新复制件与基线，验证其内容与来源清单一致；再次核实来源未变化。
5. 在首次移动目标之前写入待完成记录，记录新旧内容摘要及旧目录存在性。
6. 将旧目录移到备份槽位，依次安装两份暂存目录。
7. 核对已安装的两个目录、基线及当前来源后，移除待完成记录，作为提交点。
8. 提交后清理旧目录；清理失败返回 warning，完整的新 generation 仍然有效。

两个目录不能通过一次普通文件系统操作原子切换。提交前的真实进程退出会留下记录，后续检查返回 `incomplete_sync`。

可捕获失败触发回滚。回滚把待丢弃的新目录原子移动到 discard 槽位，再恢复完整备份；不会先递归删除活动目录。这样即使清理只做了一半，也不妨碍完整复制件的恢复和下一次清理重试。恢复自身再次中断时，依据固定槽位和内容身份继续处理，不能靠 PID 或超时抢占活进程。

若备份或目标有无法解释的外部修改，保留记录和证据，返回 `recovery_required`。首次同步没有旧 generation 时，恢复到原先不存在的状态。

## 依赖与测试 seam

文件系统属于 **local-substitutable**：真实目录与测试临时目录使用同一个 filesystem adapter。内容比较属于 **in-process**。没有第二种真实存储需求，不建立虚构的 adapter 抽象。

故障注入只使用私有文件操作 seam；结果断言通过 `check()`、`sync()`、CLI 和实际目录内容完成。进程中断使用独立 Python 子进程 `os._exit()`，与普通 exception 回滚分开验证。Windows 锁与 POSIX 锁分别使用系统实现，不能通过删除锁文件抢占。

测试保留现有行为覆盖，新增源变更/删除、不可读、关键目录缺失、基线绕过、布局错误、实际 junction、四个切换点失败与进程退出、恢复中再次退出、首次同步中断、部分清理失败、并发进程占用等场景。没有为了内部 helper 的形状再增加一层镜像测试。

## 限制

本轮验证进程退出后的恢复，不宣称真实断电、存储设备故障或远程文件系统上的持久性。来源或受管文件在任意外部进程中被持续改动时不提供跨整个文件系统的原子快照；暂存前后与发布后复检会拒绝观察到的不一致。

两个入口继续集中在 [sync_spec.py](../../tools/sync_spec.py)，没有新增跨 module 调用协议。其他五项架构候选不在本次 implementation 范围内。
