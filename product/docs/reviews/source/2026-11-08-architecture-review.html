问题四条 implementation 重复组织候选、预留、attempt、失败关闭和 fallback；修正同一取消或计费规则需要横跨多条路径。

方向将共享尝试生命周期深化到同一 module；同步响应与流式 generation 保留各自内容处理，共享约束由内部 implementation 承担。

证据同步主路径在调用前、失败后和 backoff 期间处理取消；流式主路径另有 consumerStopped、清理和 generation 规则。已共用 beginModelAttempt / finishModelSuccess，但编排仍重复。

  • locality：取消与结算同处
  • leverage：四路径共享约束
  • interface 测完整 attempt

Deletion test：删除重复编排应减少分支；共享预留、关闭规则不可删除，否则规则回流四处。目标是提高 depth，不是再加一层转调。

现有 Provider / StreamProvider seam 已有 stub 与真实协议 adapter；复用该变化点。leverage 来自一次修正覆盖同步、流式与 fallback。

验证方向 保留真实账本与本地 fake provider 验收；通过调用 interface 对照取消时点、拒绝不重试、预留释放、封存失败与 generation 隔离。

ADR / 范围 遵守 ADR 0035。job-scoped platform_model_calls 与 run-scoped operations 归属不同，不应顺手合并账本。

问题已有 shallow seam 只集中权限 SQL；可读性、封存字节完整性与读失败分类仍由调用者组合，普通读取与缓存命中的校验深度不同。

方向在组织知识库 module 内收拢片段读取与验证，使策略差异成为显式决定；先核实完整性要求，再统一 implementation。

证据缓存命中核对正文与 body_sha256；rankRetrieval 虽查询了哈希，读正文时未执行该比较，GetChunk 也只调用受大小限制的 readChunkText。权限条件已经统一。

  • locality：可读性规则集中
  • leverage：三入口共用验证
  • interface 测实际返回正文

Deletion test：readChunkText 几乎只包 Open / ReadAll；深化它可吸收三条路径的验证知识、提高 depth。不能为减少代码而删除命中复检。

seam 仍位于授权后的片段读取；本地 objectstore adapter 与真实 PG 已可测试。不把组织知识库规则泛化到整个对象存储。

验证方向 通过 Query / GetChunk / Answer 对照缓存开关：正文损坏、对象缺失、瞬态故障、撤权与索引替换；保留四类 RAG 失败分类。

ADR / 范围 保持 ADR 0015 的命中正文复检、瞬态失败保留缓存行，以及 ADR 0018 的活动索引约束。静态差异不直接等于越权或泄漏。
