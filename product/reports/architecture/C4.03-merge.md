## 冷启动竞态（异常记录）

新增模块首次在集成 tip 运行时，取消用例出现两次计时相关失败；同一代码树在 WSL/runsc 暖机后
连续两次整模块通过。失败点与机制：

- 第一次：`assert evidence["sandbox_started"] is True` → `{'started': True, ..., 'sandbox_started':
  False, 'heartbeats': 3, ...}`（`pytest-c4_03-scheduler-regressions.log`）。
- 第二次（单条复跑）：`assert evidence["started"] is True` → `started`/`sandbox_started` 均 false，
  `heartbeats: 2`（`pytest-c4_03-cancel-rerun1.log`）。
- 机制：test-owned 触发器在 attempt **第一个 heartbeat** 后写入 `cancel_requested_at`；按
  `internal/sandbox/executor.go` 的设计，第一个 heartbeat 发生在 sandbox 启动**之前**，取消由
  下一次 50ms ticker 观察到。WSL/runsc 冷启动时，ticker 可能在任何 runsc 进程出现前触发：
  独立 cleanup 的 PID 为 0 → `SandboxStarted=false`；两个 python 分支都未真正启动时，
  `s.started=false`，exit 证据以 `started=false` 确认。测试断言取消发生在“已启动 sibling”上，
  因此对冷启动延迟敏感。
- 判定：不是合并回归。合并树与票分支最终树逐字节一致（tree `351c0fb`），票报告最终树
  `7fff4a0` 的 `C4.03-raw/final-pytest-c4-03.log` 记录同一用例 2 passed/56.09s；暖机后本 tip
  连续两次 2 passed。确定性排空顺序由 Go seam `TestGraphRunCancellationDrainsStartedSiblings`
  覆盖，该测试不依赖真实 runsc 启动时序，且在本次 142 PASS 中通过。
- 处理：未修改、未放宽、未跳过该真实栈测试，也未修改产品代码；保留两次失败原始日志。建议后续
  （下一票或 follow-up）把取消注入点改为“观察到首个 sandbox 单元真实启动后”再写取消意图，或在
  套件内预热 WSL/runsc，以消除冷启动竞态；在此之前该用例在冷机首次运行可能红。
