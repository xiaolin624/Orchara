## 2. 实现变更

### 2.1 `internal/capabilities/service.go`

- 新增 `cleanupContext(ctx)`：`context.WithTimeout(context.WithoutCancel(ctx), 5s)`。清理不是 provider
  工作，不派发、不重试、不自造费用；脱离已取消请求才能把事实写完，固定上界避免挂死。
- 新增 `cleanupFailure(cause)`：500 `internal_error` + 安全文案 “the model operation ledger could
  not be closed”，原始 DB 错误通过 `Error.Unwrap` 关联（只对 `errors.Is/As` 可见，不进正文/日志）。
- 新增 `cancelledFailure(code)`（两个稳定取消码共用安全文案）。
- 新增关闭助手，全部使用有界独立上下文并把失败显式返回：
  `closeOperation`（operation 级）、`closeIfAuthorized`（只关仍 `authorized` 的行）、
  `closeAttemptAndOperation`（attempt+operation 原子关闭）、
  `closeAfterProviderFailure`（provider 已应答后的关闭 + usage 结算，先查 attempt 仍
  `dispatching` 再写，幂等）。
- `finishCancelled` 改用 `cleanupContext`；关闭失败返回 `cleanupFailure` 而不是“已按取消关闭”。
- `resetAttemptForRetry` 内部改用 `cleanupContext`：失败 attempt 的 provider 事实必须在调用者消失时
  仍然持久；其后由驱动重查请求 ctx 决定是否继续。
- `finishModelSuccess` 收敛为单一 `failClosed` 终态路径：校验失败、编码失败、事务启动失败、封存失败、
  定价缺失、settle/attempt/operation/fallback/commit 失败都先回滚再关闭；关闭失败优先返回
  `cleanupFailure`，成功则返回原 typed 错误（维持既有 422/429/500 词表）。
- `selectFallback` 增加 `providerFor` 参数（nil 回退 `Providers.For`），与派发使用同一 seam。
- `failOperation` 返回原始写错误（调用者决定是显式清理失败还是已有更具体结果的 best-effort 写）。

### 2.2 `internal/capabilities/attempt.go`

- `refuse`：预派发拒绝的 operation 关闭走 `closeOperation`（有界独立 ctx）；关闭失败返回
  `cleanupFailure`，不再出现“返回 422 但 operation 仍 authorized”的幽灵。
- `dispatch`：非 fallback 终态关闭走 `closeAttemptAndOperation`；reset 之后、`selectFallback`
  之后重查请求 ctx；`begin` 失败且 ctx 已取消时只关 `authorized` 行并返回取消。
- 新增 `finishContent`：`Complete` 错误是终态（不重试/不 fallback），但若内容半边未能把 attempt
  写关闭（封存期间请求死亡、表被锁），驱动用同一有界清理上下文补关并结算真实 usage；补关失败返回
  `cleanupFailure`，绝不返回一个暗示“已关闭且已记账”的内容错误。
- `stopOperation` 走 `closeOperation`；`dispatchFallback` 的 begin 失败/终态失败同样处理。

### 2.3 `internal/capabilities/stream.go`

- 流式装配不一致（generation 文本 ≠ provider 完整文本）的关闭改走 `closeAfterProviderFailure`；
  关闭失败时先投递 `internal_error` 终态帧，再返回 `cleanupFailure`，不把“未关闭的账本”说成 422 装配拒绝。

### 2.4 `internal/capabilities/errors.go`

- `Error` 增加未导出 `cause` 与 `Unwrap()`；`cleanupFailure` 用安全状态/码呈现，数据库原因只关联不暴露。

### 2.5 `internal/capabilities/fallback.go`

- 删除无调用者的 `fallbackPhysicalAttempts`；注释改为“fallback 一次由驱动结构保证”。

## 4. 四路径 × 取消点矩阵

物理请求数 = 该 operation 真正发出 wire 请求的次数（T122 fake provider `requests()`；stub 的
in-process 调用由 attempt 行证明）。attempt/operation 均指 `platform.operation_attempts` /
`platform.operations` 的最终行。

| 路径 | 调用前（尚未建立物理 attempt） | 调用中 | 退避 | 重试/fallback 通知 |
| --- | --- | --- | --- | --- |
| 同步主 | Go `TestCancelledBeforeTheFirstAttemptDispatchesNothingAndClosesTheOperation`：0 次物理调用、0 个 attempt 行、operation 以 `caller_cancelled` 关闭；驱动循环顶部/`begin` 失败后检查 | `test_cancellation_during_the_sync_call_closes_as_caller_cancelled`：1 请求、1 attempt `caller_cancelled`+`released`、0 charge、无 receipt、不重试/不 fallback | 共用驱动 `sleepBackoff`；同步 HTTP 路径无确定性 20–40ms 窗口，单列 `not_run`（见 §7） | N/A：同步内容没有临时通知帧（只在终态决定后写响应体） |

## 7. 解释 / 取舍 / 限制

**封存本身绑定请求，失败后的清理与结算脱离请求。** 调用者在封存期间断开时，success 事务按原语义
失败（不把客户端从未收到的成功强行提交）；失败处理用有界独立上下文把 attempt/operation 关闭并按
既有规则结算真实 usage。账本码是 `internal_error`（平台无法提交一个完整应答），不是
`caller_cancelled`：后者在既有 T122/T046 规则里必须释放且不收费，而这里 provider 已真实消费。
这样同时满足“完整响应后的消费不消失”“取消码语义不混用”“不留下 dispatching”。

**`resetAttemptForRetry` 也脱离请求。** 失败的物理尝试及其预留释放是 provider 已发生的事实，必须在
调用者消失时仍落库；驱动随后重查请求 ctx，已取消则 `stopOperation`，不会开始下一次尝试。

**`begin` 因取消回滚后只关 `authorized`。** `closeIfAuthorized` 条件更新避免把已记录终态（如预算拒绝、
重放成功）改写成取消；`finishCancelled` 仍用于循环顶部/调用中已确定取消的路径。

**清理失败显式返回而非伪装修复。** 返回 500 `internal_error` 并关联原始 DB 错误；调用方无法把它当作
“已干净关闭”的取消/拒绝。本票不重试清理写、不重复物理请求“补救”记账失败；若数据库本身拒绝提交，
行可能仍 `dispatching`，这正是需要被观察到的失败，而不是被吞掉。

**adapter 路由差异是潜在差异。** 两个已编译 adapter 都实现 `StreamProvider`，因此 `For` 与
`StreamingFor` 在选择阶段当前不会给出不同答案；修正消除的是 seam 不一致本身（选择与派发统一），
没有为制造分歧新增 provider 或生产注入点。

限制 / `not_run`：

- **真实厂商 provider：`blocked` / `not_run`。** 本机无获批厂商端点、凭据、配额与外发批准；本票证据
  全部来自 dev stub 与 T122 的本地 loopback fake HTTP provider，未用 stub/fake 冒充真实厂商。
  真实厂商的 usage/价格、429/流式/工具调用行为：`not_run`。
- **同步 HTTP 路径的“退避中取消”确定性窗口：`not_run`。** 退避为 20–40ms 且同步内容没有临时通知帧，
  Python 客户端无法像流式通知那样稳定命中；该分支是同步/流式共用的同一 `sleepBackoff` +
  `stopOperation`，由流式真实栈用例与 Go 单测覆盖。
- **“请求 ctx 仍存活但 emit 失败”的真实 socket 场景：`not_run`。** 真实 HTTP 消费者的通知投递失败
  可达形态就是消费者消失（ctx 先被取消，驱动在分类阶段即按取消短路）；内容半边的发射错误传播由 Go
  单测固定，驱动的 `stopOperation` 与退避/fallback 停止共用同一真实栈路径。
- **封存失败产生的对象目录孤儿字节：** `sealTx` 先写对象再写行，事务回滚后对象由既有 orphan-sweep
  边界处理；测试断言“无 artifact 行 / 无 receipt”，不关闭或清空目录（不改变既有对象存储语义）。
- `go test -race`：`not_run`。
- 全量 `pytest tests`、`tests/f00b`/`f03`/`f05`：按本票门禁 `not_run`（最终集成票负责全量）。
- 浏览器 DOM：不适用（本票无页面改动）。
- 跨父子 run 的并发预算 e2e：沿用 T046 边界，`not_run`。
