## 用户故事

自动化维护者在多个进程或不同操作系统上使用相同的检查、同步命令时，得到一致的
成功/失败含义；工作区被占用时快速报告 `busy`，释放后恢复正常操作；两个实际进程
共享同一个工作区互斥，竞争者不能靠删除锁文件或猜测 PID 抢占；Windows 完整工具
回归与真实目录重定向，以及 POSIX 来源变化、同步和进程锁，都有可复核的实际结果，
并区分完整套件与有限冒烟证据。

## 复现并修复的真实缺口（POSIX 锁文件删除）

**红（修复前）**：`C1.04-posix-probe-red.txt` 记录 WSL 真实进程：父进程持有 `fcntl` 锁，
`lock.unlink()` 成功后，真实 CLI `--check` 输出 `no drift` 并 exit 0，`--sync` 输出
`copied 3 files` 并 exit 0——持锁者仍存活，锁却已被第二个工具进程取得。原因是 POSIX
允许 unlink 已打开的锁文件，第二个进程在**新 inode** 上加锁成功。

**修复**：`product/tools/sync_spec.py` 的 `_locked()` 在 POSIX 下先用 `os.open(state)`
+ `fcntl.flock(LOCK_EX | LOCK_NB)` 锁住固定的私有状态目录，再锁锁文件；状态目录是
权威互斥，删除锁文件不再能交给新的工具进程。Windows 分支保持原有 `msvcrt` 字节范围锁
（OS 本身阻止删除打开的文件）。公开接口/CLI 未变，恢复代码未动。

**绿（修复后）**：同一 WSL 探针 **22/22 passed, exit 0**（`C1.04-posix-probe.txt`）：
unlink 仍成功（POSIX 语义），但 check/sync 竞争者在删除后仍快速 `busy`，holder 存活，
受管内容不变。

**测试敏感性**：临时把 Windows 的加锁与解锁都改为 no-op，运行本票 8 项 →
**5 failed, 3 passed**（失败均集中在互斥与 release 行为，3 项非锁测试仍过），见
`C1.04-mutation-sensitivity.txt`；随后按原字节恢复，`sync_spec.py` SHA-256 仍为
`CE2E7770068025F3FE416B53B7B4A011079B30C114366F8D2041D6475E78E80E`，无变异残留。
