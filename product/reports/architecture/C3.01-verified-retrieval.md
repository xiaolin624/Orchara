## 1. 交付内容

### 1.1 新 module：`internal/knowledge/reader.go`

owner 限定的 readable-chunk module（设计文档 C3 方案 C，吸收 A 的有界批量）。一个 request
绑定一个 owner，不缓存授权决定，不是跨请求 session。三个有意义操作 + 一个共享的字节校验
原语：

```go
// 对象存储只需这一个能力（单元 seam 可据此计数 open/read，不包生产 store）
type chunkBodyReader interface {
	Open(key string) (io.ReadCloser, int64, error)
}

// 绑定当前请求的 owner id
func (s *Service) reader(ownerID string) chunkReader

// 检索候选：一次有界 metadata SQL + 逐候选一次有界读取/摘要/长度校验；
// 返回通过校验的片段 + 被跳过数（>0 表示 partial，调用者不得缓存）
func (r chunkReader) Candidates(ctx context.Context, baseID, modelRevision string) ([]readableChunk, int, error)

// 单片段打开：同一谓词/投影/字节校验；任何不可读/不可验证都是 ErrNotFound
func (r chunkReader) Open(ctx context.Context, chunkID string) (readableChunk, error)

// 缓存命中复检：同一谓词/投影/字节校验 + 与缓存条目 provenance/正文对照；
// 返回 (ok, ADR 0015 D6 既有 reason 词表)
func (r chunkReader) CheckCached(ctx context.Context, baseID string, items []retrievalCacheItem) (bool, string)
```

内部结构：

- `readableChunkColumns`：**唯一** metadata 投影，含 chunk 身份/引用/embedding 与正文
  artifact 的 `coalesce(a.sha256,'')`、`a.size_bytes`、`a.object_key`。SQL 不把
  NULL/非法完整性 metadata 过滤掉——必须让它到达校验器并计为 skipped，否则损坏候选会被
  静默当成"完整结果"而被缓存。
- `currentReadableChunkSQL`（既有 `readable_chunk.go`）：三个操作都只追加自己的候选谓词，
  不复制权限策略。owner/tombstone/active ready index/正文归属条件逐字未改。
- `chunkCandidate.readVerifiedBody`：先拒绝缺失/非法 metadata（`sha256` 非 64 位小写 hex、
  `size_bytes` NULL/≤0/>协议上限 → **不打开对象**），再 `Open` 一次，用
  `io.LimitReader(io.TeeReader(reader, hasher), size_bytes+1)` 单次读取：同一 pass 累计字节
  数并计算 SHA-256；**字节数 == size_bytes 且摘要 == sha256** 才返回文本。不读宿主
  `stat`/`Open` 返回的 size 作为证明。对象只 open/read 一次，不存在"为算两个值打开两次"。
- 失败分类（内部 `chunkBodyError`，不外泄对象键/路径）：`metadataInvalid` /
  `unreadable`（确定性：`ErrNotExist`/`ErrInvalidKey`/`ErrTooLarge`）/ `integrityMismatch`
  （长度或摘要不符）/ `unavailable`（I/O 等瞬态）。`Error()` 固定文案，不拼接 cause；
  三个调用者按各自业务映射（检索跳过、打开 404、缓存 reason）。
- SQL 整体失败与逐对象失败严格分开：`Candidates` 的 query/scan/rows 错误作为 error 返回
  （→ API 500）；逐对象失败只增加 `skipped`，请求仍 200。

## 4. 新增校验成本（记录，不作毫秒断言）

- **功能守卫（成本形状）**：每个候选恰好 **1 次 open + 1 次有界 read + 1 次 SHA-256**；
  读取上界 = `size_bytes+1`，因此超长对象最多多读 1 字节就会被长度判据拒绝（Go 测试
  `TestReadVerifiedBodyRefusesAWriteThatExceedsTheAuthoritativeSize` 断言实际读取
  `len(original)+1` 字节），不会把整段损坏对象读完；metadata 缺失/非法时 **0 次 open**
  （`TestReadVerifiedBodyRefusesUnusableMetadataBeforeOpeningAnything`）。没有"为得到长度和
  摘要分别打开一次对象"。
- **真实 retrieval 端到端**：7 个候选 / 14,671 正文字节，冷请求（cache miss、需写缓存）
  27.293 ms（同日另一次 29.185 ms，merge 后 45.624 ms；宿主负载不同）；同时逐项断言返回
  正文的 UTF-8 字节数 == `artifacts.size_bytes` 且 SHA-256 == `artifacts.sha256`。粗守卫是
  30 s 功能上限，不是延迟目标；绝对延迟随宿主负载变化，不承诺性能提升。
- **单 body 校验成本**：真实本地 objectstore，~2.9 KiB 正文，`BenchmarkReadVerifiedBody`
  2439 iterations 0.445 ms/op（另一次 3552 iterations 0.340 ms/op），主要成本是 Windows
  文件 open；SHA-256 本身对 chunk 尺寸（≤1200 rune）为微秒级。相对迁移前 `readChunkText`
  （open+read、无摘要）新增的是：同一份 `size_bytes` 列（同一条 SQL，无额外查询）、一次
  SHA-256、以及长度比较；**没有新增对象 open**。
- 记录方式：`C301-COST` 行（focused 套件 stdout，`-s`）、Go benchmark 输出，均保存在
  `reports/architecture/C3.01-focused-suite.txt`、`C3.01-go-tests.txt`。
