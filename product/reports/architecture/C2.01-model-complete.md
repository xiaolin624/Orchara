## 1. 交付内容

### 1.1 私有统一尝试驱动（`internal/capabilities/attempt.go`，新增）

设计 C 的 operation session：外部仍只有 `Invoke` / `Stream`，session 是包内私有结构。

- `modelAttemptSession`：持有已准备 operation 的身份、run/params/spec，是“一个逻辑模型操作”
  的尝试生命周期所有者。
- `candidate(profile)`：候选解析（`Providers.For` + `Available`）→ 实际候选费率
  （`priceForProfile`）→ 保守预留（`reservationFor`）。全部在物理调用之前。
- `begin(...)`：复用既有 `beginModelAttempt`（operation CAS + `ReserveTx` 原子预留 + attempt
  行，同一事务）；预算拒绝沿用其“0 attempt、operation failed”的既有语义。
- `dispatch(...)`：统一驱动主候选最多 3 次物理尝试、兼容 fallback 最多 1 次；负责取消检查、
  错误分类、退避、失败预留释放、fallback 选择与账本关闭。
- `dispatchFallback(...)`：一次 fallback 尝试；失败按自身错误码记账，不伪造成功。
- `classifyModelFailure(...)`：把“可重试”（仅 typed transient）与“允许 fallback”
  （availability 类）拆成两个独立判断；取消单独短路。
- `modelContentHandler`：内容处理半边（`Call` 一次物理请求；`Complete` 消费完整响应）。
  同步路径的 `Complete` 是既有 `finishModelSuccess`（校验/封存/结算），其错误是终态，
  不回退、不重试——保留“完整响应后平台校验/封存失败仍按真实 usage 结算”的既有规则。

### 1.2 `service.go` 收敛

`dispatchModel` 只装配 session + 同步内容处理；原 `dispatchModel` 内联循环与原
`dispatchFallback`（候选解析/预留/关闭/结算的重复编排）删除，`service.go` 净减 144 行左右。
`Invoke` 的授权、幂等/operation、manifest 校验、params hash、tool/connector 分支、响应形状全部
未变；私有 `dispatchModel` 只去掉了未使用的 `digest` 形参。`beginModelAttempt` /
`finishModelSuccess` / `resetAttemptForRetry` / `failModelAttemptAfterProvider` /
`selectFallback` / `budgetAllowsFallback` 保留原实现并被 session 复用。

### 1.3 发现并修复的两处真实行为差异（先红后绿）

**(a) adapter 类可用性错误在主路径被重试，fallback 路径与流式路径不重试。**
旧 `dispatchModel` 用 `fallbackReasonFor` 同时决定“是否重试”和“是否 fallback”，于是
`ErrAdapterUnavailable` / `ErrNotConfigured`（availability 类、T122 分类表明确“不重试”）
在同步主路径被物理重试 3 次，而同一错误发生在 fallback 尝试时只花 1 次（流式主路径也只花
1 个 generation）。复现：`stub-adapter-down-primary` + 兼容 fallback，旧代码 attempts
`[1,2,3,4]`，新规则 `[1,2]`。修复：重试只由 typed transient 决定；availability 类直接进入
fallback 评估。主候选的三次上限、fallback 的一次上限不变。

**(b) 派发前拒绝后主路径遗留幽灵 `authorized` operation。**
旧 `dispatchModel` 在 operation 行已存在、但实际费率/预留解析失败（例如 profile
`price.input_per_million` 不是十进制）时直接返回 422，operation 永远停在 `authorized`，
重放得到 409 `operation_in_progress`——一次从未发生的调用却像一个在途操作。同一类拒绝在
fallback 路径（`dispatchFallback`）和既有预算拒绝（`beginModelAttempt`）里都会把 operation
记为 failed。修复：session 的 `refuse` 用同一 typed code 关闭 operation（0 attempt、0
ledger 行），重放返回已记录的失败，零物理派发。

两处均先以失败测试复现：`C2.01-red-pytest.txt`（`[1,2,3,4] == [1,2]` 失败；
`authorized == failed` 失败），再由 `b3104bb` 转绿。

## 5. 解释/取舍（已接受行为的边界）

- **重试谓词**：按票面“typed transient 重试 / availability fallback 分开”与 T122 错误分类
  （`adapter_unavailable`、`provider_not_configured` 不重试）收敛为“仅 typed transient 重试”。
  因此 adapter 类故障现在 1 次物理主尝试后直接进入 fallback，不再消耗剩余重试；主候选上限仍
  是 3、fallback 仍是 1，权限/Schema/工具参数仍 1 次即终止。
- **attempt_no 稠密规则**：迁移 0025 明确 “attempt_no starts at 1 and is dense per operation”。
  fallback 使用“最后一个主尝试号 + 1”，因此三次重试后的 fallback 仍是 attempt 4（T045 既有
  证据不变），adapter 类早退时是 attempt 2，不留空洞。流式路径当前仍固定用
  `maxPhysicalAttempts+1`，其 adapter 类早退会留 `[1,4]` 空洞；该差异由 #147 接入同一 session
  时消除（本票未迁移流式，见 §6）。
- **派发前拒绝的账本路由**：operation 已记录、但实际费率/预留不可用（之前主路径遗留
  `authorized`）现在与 fallback 路径/预算拒绝一致：operation failed + typed code + 0 attempt。
  这是本票修复的第二处真实差异，不改变任何既有成功/失败路径的状态机。
- **取消检查**：fallback 尝试前也执行与主路径相同的 `ctx.Err()` 检查（H2 规则），因此取消后
  不会为 fallback 开启一条“从未发生”的 attempt。普通调用取消、流式取消、预算拒绝、缺 usage
  的既有码与记账未改。
- `failOperation`/清理写失败沿用既有 best-effort 语义；#148 负责“清理失败明确返回/关联”。
